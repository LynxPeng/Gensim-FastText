# 原论文全量复现：性能瓶颈与耗时估算

估算时间：2026-10-08 22:05（北京时间）。基于本机已完成的 AG News、Sogou News 运行及当前代码；YFCC 全量模型尚未完成，相关耗时为规划区间，不能视为实测或完成承诺。数据下载已完成，不计入下列区间。

## 比较范围与 API 核查

**下文比较的是两种实验方案的耗时，不是同一算法在两个框架中的速度。不能据此得出“Gensim 比原生 FastText 慢多少”的结论。**

Gensim 4.4.0 的 `FastText` 实现对应《Enriching Word Vectors with Subword Information》：通过上下文和字符子词学习词向量。原生 `fasttext.train_supervised` 对应《Bag of Tricks for Efficient Text Classification》：根据文档标签联合学习输入表示和分类器。当前 Gensim 路线还要生成文档向量、训练外部分类头，因此计算量与训练目标均不相同。

本机核查确认：`hasattr(gensim.models.FastText, 'train_supervised')` 为 `False`；训练已加载 `fasttext_inner.cp312-win_amd64.pyd` 与 `fasttext_corpusfile.cp312-win_amd64.pyd`，实际调用使用 `corpus_file` 和 20 个线程。Gensim 没有原生监督 FastText 分类入口，且 `word_ngrams != 1` 会抛出 `NotImplementedError`。`hs=1` 只改变词预测的训练目标，不会将词向量模型变成标签分类器。

Gensim 的编译内核和文件语料接口是对其实现的优化；这不保证其在所有任务中快于原生 C++ 库。真正比较无监督训练实现的速度，需要以同一语料，对齐 CBOW/Skip-gram、维度、窗口、负采样、子词、桶数与线程数，将 Gensim 与原生 `fasttext.train_unsupervised` 分阶段计时。目前未完成这种基准，本文不作框架性能排名。

核查依据：[Gensim 4.4.0 源码](https://github.com/piskvorky/gensim/blob/4.4.0/gensim/models/fasttext.py)、[原生两类训练 API](https://fasttext.cc/docs/en/python-module.html)、[本项目调用](../gensim_lab/paper_worker.py)。

## 主要瓶颈

1. **Gensim 的字符子词和上下文训练。** 当前路线对词进行无监督 CBOW、字符子词与负采样训练，再拟合分类器；原生路线按文档联合监督训练。Sogou 单轮有 2.61 亿词，五轮约 13 亿原始词；两条路线的更新粒度和目标不同，所测倍率反映当前方案的计算量差异。
2. **单线程文档聚合与重复解析。** `document_vector` 在 Python 中计词频、查向量、累加并归一化。YFCC 有 9,119 万篇文档，每个维度和种子均生成自己的特征；标签编码与数据扫描也在 CPU 上执行。
3. **YFCC 的内存、磁盘与预测开销。** float32 文档矩阵在 50 维时为 18.24 GB，200 维时为 72.95 GB，合计每个种子 91.19 GB，三种子约 273.6 GB。使用磁盘映射，仍有读写成本。外部标签分类头在 CUDA 上训练，精确 Huffman 树预测在单个 CPU 线程上执行，实际搜索量尚未测得。
4. **完整核验开销。** 全部测试预测写盘后，还要加载模型、重新预测并核对全部验证/测试记录；模型哈希和报告编制也占用时间。当前八套分类数据预计约 12.9 亿训练词，其中六套仅作轻量抽样估计。

实现位置：[文档聚合与评估](../gensim_lab/paper_worker.py)、[外部标签分类头](../gensim_lab/paper_hs.py)。CUDA 当前覆盖标签分类头，其前面的 Gensim 训练、文档聚合与后面的树搜索仍使用 CPU。

## 全量耗时预算

“一遍”指一个种子：八套分类数据，以及 YFCC 的 50/200 维。原生路线包括 unigram/bigram，共 20 个模型；Gensim 两阶段路线共 10 个模型。包含训练、评估、完整重载检查与输出，使用当前 20 线程配置。

| 范围 | 原生 FastText | Gensim 两阶段近似路线 |
| --- | --- | --- |
| 八套分类数据，一种子 | 约 10–40 分钟 | 约 2–3 小时 |
| YFCC 全量，一种子 | 约 1–4 小时 | 约 10–30 小时 |
| 两个实验全量，一种子 | 约 2–6 小时 | 约 12–36 小时 |
| 当前三个种子 | 约 6–18 小时 | 约 36–108 小时 |

两条路线合计 90 个运行，目前顺序执行，建议按约 **2–5 天** 安排。初次清洗、词表与特征准备可另有共享开销；范围已留余量，但 YFCC 200 维训练及精确树预测可能使上限继续增加。

八套分类的区间由已测吞吐和训练词量外推。YFCC 的区间结合约 9.50 亿保留训练词、50/200 维的计算与内存增长，以及额外文档聚合、CUDA 分类头和核验开销作宽范围预算；尚无本机 YFCC 完整运行可以验证该区间。维度增长不能简单当成耗时严格线性增长。

[词量与矩阵体积估算](../artifacts/paper_reproduction/runtime_volume_estimate.json)记录了实测量与估计量的区别。六套分类数据以八个字节位置附近的连续行估计平均长度，属于粗略运行预算抽样，不是无偏文章抽样，也不是分类实验结果。

## 可优先优化的部分

优先验证文档聚合的批量计算或 Numba/CUDA 实现，以及一次标签编码在多个维度和种子之间的复用；改变算法前需检查向量与预测一致性。另可调整串行队列，先完成原生全量结果，再执行耗时较长的 Gensim 路线，以便更早获得论文监督模型的复现结果。这些是优化候选，当前训练与队列没有因本次估算而修改。
